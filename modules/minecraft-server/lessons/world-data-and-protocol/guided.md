# Reading world data and speaking the protocol

<!-- Generated from core.md. Substantive fixes belong in core.md; regenerate rather than fork. -->

## What this is

The server's logs were its diary — an account of what happened, written for humans. This
session reads the server's data in two places where no diary exists: **at rest**, in the
world folder's own files, and **in motion**, on the wire between two programs.

First, the files. The world folder isn't an account of the world; it *is* the world. Every
block placed, every player's position, the time of day, the seed the terrain grew from —
all of it sits in files inside `world/`, and files can be read by programs you write.
There's a catch, and this session meets it head-on: these files are not text. Open one in
an editor and you get gibberish, because the bytes don't encode characters — they encode
structure directly. So this is the session where you learn to read your first **binary
format**, and that half ends with something better than printed text: a map. Every
player's position in the world, plotted as labeled dots on an image you can post where the
people on it will see it.

Then, the wire. When you changed your server's message of the day, it appeared on the
multiplayer screen without anyone joining — and you were told why: the game pings every
server on the list, and each server answers with its name, message, and player count. A
tiny conversation between two programs, which you were promised you'd one day speak by
hand. Today. No library — a raw socket and bytes you assemble yourself, following the same
protocol documentation the authors of every Minecraft library and bot were reading when
they built the tools you've used. Your script will ask your own server to describe itself,
then ask one of the biggest public servers on the internet the same question — and get the
same kind of answer, because your bytes are correct and correctness is the only membership
card this conversation checks.

Two halves, one lesson, because they are secretly the same lesson — and by the end you'll
be able to say precisely how.

## New tools

**NBT — Named Binary Tag** — is Minecraft's own file format for structured data. It's a
tree: named, typed entries nested inside each other, the same shape as the JSON you've
read before — but encoded as compact bytes instead of readable text. `level.dat` (the
world's global state) and every file in `playerdata/` are NBT.

**gzip** is a general-purpose compression format — same family as the `.zip` files you've
met. Minecraft compresses its NBT files with gzip, so there are two layers between you and
the data: gzip on the outside, NBT inside. You brushed against gzip once before without
naming it — the older log files in `logs/` end in `.gz` — and today it gets handled
properly. Python includes a `gzip` module in its standard library, nothing to install. One
useful fact: every gzip file begins with the same two bytes, `1f 8b` (in hexadecimal).
Bytes like these are called a **magic number** — a signature at the start of a file that
announces its format, which is how tools know what a file is without trusting its name.

**The `file` command** ships with macOS. Run `file somefile` in the terminal and it
reports what the file actually is, by reading its signature bytes.

**An NBT library from PyPI.** The leading candidate is called **nbtlib** — but libraries
change hands and go quiet, so part of this session is checking its current state yourself
before installing, exactly the way you evaluated a library in
[Choosing a version](../choosing-a-version/guided.md): README, issue tracker, recent
releases. The installing itself is the pip routine you already know.

**matplotlib** is the standard Python plotting library — it turns lists of numbers into
charts and images. Installed with pip like anything else. You'll use a tiny corner of it:
putting dots on axes and saving the result as a PNG. Its own documentation covers the
rest, and you'll be pointed there.

**A socket** is the operating system handing your program a two-way byte pipe to another
program, named by an address and a port. That's the whole definition. When you joined your
server, the game opened a socket to it. Under your RCON scripts: a socket. Mineflayer:
sockets. Web browsers: sockets. Everything you have ever done between two programs sat on
one of these pipes; today you hold the pipe directly. Python's `socket` module is in the
standard library — nothing to install. Three calls carry the whole second half:

- `socket.create_connection((host, port), timeout=5)` — connect, get a socket back
- `sock.sendall(data)` — push bytes in
- `sock.recv(n)` — pull bytes out

One fact about `recv` that you could not guess and that has burned every person who ever
touched sockets: **`recv(n)` returns at most n bytes — whatever has arrived so far, not
what you asked for.** If you need an exact number of bytes, you loop until you have them.
Hold onto that; you'll see that the protocol is designed around it.

**The protocol documentation.** The Minecraft protocol is documented, in exact
byte-by-byte detail, by the community — this documentation is what every library you've
used was built from. It has lived at more than one address over the years (its historical
home was a site called wiki.vg), so finding its current one is part of the work below:
you'll search for **Server List Ping** and confirm you've landed on the page that
specifies the ping packet by packet, with field tables.

**The shape of the conversation**, so the spec reads as confirmation rather than mystery.
After you connect, everything both sides say is **packets**, and every packet has the same
frame: a length, then a packet id, then the fields. Your side sends two packets — a
**handshake** (protocol version, the hostname you're connecting to, the port, and a "next
state" value where 1 means "I'm here for status") and then an empty **status request**.
The server sends back one packet containing a string of JSON. Strings on the wire are a
byte-length followed by that many bytes of UTF-8 — the length prefix is what tells the
reader when to stop, which is exactly the problem `recv` just told you about.

The lengths and ids in all of the above are encoded as **varints**: a way of writing
integers that spends bytes only as needed — seven bits of the number per byte, lowest bits
first, with the high bit of each byte flagging "more bytes follow." Small numbers cost one
byte instead of four. The spec describes this precisely, and implementing it is one of
your goals below.

Two small Python conveniences, given now so the spec is the only puzzle:
`struct.pack('>H', port)` produces the two-byte big-endian unsigned short the handshake
wants for the port, and calling `.hex()` on any bytes you've built lets you eyeball them
against the spec's tables.

One rule frames the first half: **all file reading happens on a copy of the world, taken
with the server stopped.** Reading can't damage files — but you'll prove to yourself
before the end of this session why reading live files can't be trusted either.

### Meet a binary file

Open `~/projects/world-lab/world/level.dat` in VS Code and read what VS Code tells you

Then look at the raw bytes yourself. In Python (a one-liner in the interactive prompt is

```python
print(open('/Users/YOURNAME/projects/world-lab/world/level.dat', 'rb').read(4))

The `'rb'` means "read bytes" — you're asking for the bytes as they are, not as text. Look

```

Three observations: what VS Code said, what the first bytes are, what `file` reported.

### Whose file is whose

Now `playerdata/`. One file per player who has ever joined — but the filenames are UUIDs.
A **UUID** (universally unique identifier) is a huge random number written as hex with
dashes. The files are keyed by UUID instead of player name for a simple reason: names can
change — Mojang lets players rename — and the UUID never does. If the files were named by
player name, a rename would orphan someone's entire inventory.

Your goal: for each file in your copy's `playerdata/`, determine which player it belongs
to — by matching facts inside the file against facts you can check in-game, not by asking
the internet.

<details>
<summary>What kind of fact could match?</summary>

Each file records things a player could check about themselves while standing in the
world. Open the F3 debug screen in-game and look at what it shows you. Which of those
things must the file also contain?

</details>

<details>
<summary>The matching fact</summary>

`Pos` holds three numbers — x, y, z, exactly what F3 displays. One thing to keep
straight: your copy is a snapshot. The positions in it are where players were when you
made the copy, not where they are right now. Experience level and what someone was
carrying make good cross-checks.

</details>

<details>
<summary>A cross-check the server keeps for you</summary>

the server folder — and you can read JSON. Look through the server folder's top level for

</details>

### Now the wire

The files were the world at rest. The same server also *speaks* — and the second half of
this session builds the ping script byte by byte. The remaining goals come with success
criteria and not much else: you have every ingredient, and the assembling is yours.

Step zero, before any code: find the protocol documentation's current home — search for
**Server List Ping** and confirm you've found the page with the packet-by-packet field
tables. Then **skim the entire page.** Not studying — skimming, top to bottom, once. See
how big it actually is, notice the packet tables, notice that it ends. You scrolled the
whole NBT tree an hour ago; this is the same move on a real protocol spec, and it's the
last new kind of surface this module has to show you.

### Silence is data

Connect a raw socket to your own running server at `localhost:25565` and send nothing.
Watch what happens.

Done when you can answer, from observation: who closed the connection, and after roughly
how long? (`recv` returning empty bytes — `b''` — is how a socket tells you the other side
hung up. Measure the wait; `time.time()` before and after is enough.)

What this establishes: connecting is not communicating. The server accepted the pipe,
then waited for you to speak first, then gave up on you. Every result in this half,
including nothing happening, is information.

### Varints, tested alone

Implement two functions from the spec's description of varints: `write_varint(n)`
returning bytes, and `read_varint(sock)` reading one varint off a socket.

Then — before any socket touches them — test them by themselves. The spec's page includes
a table of example values with their exact encodings. Done when:

- `write_varint` reproduces every example in the table (compare with `.hex()`)
- feeding `write_varint`'s output back through your reader returns the original number,
  for every example (reading from bytes instead of a socket is fine for the test — or
  connect to your server and ignore what you receive)

Testing a piece by itself before trusting it inside the whole has a name — a unit test —
and this is the situation that justifies the habit: a wrong varint encoder inside a full
ping doesn't produce an error message. It produces silence, with nothing pointing at
which of your forty lines is wrong. Ten minutes of table checking is the difference
between debugging one function and debugging everything at once.

<details>
<summary>If the encoder fights back</summary>

Attempt it from the spec first — the description is complete. If you're going in circles,
here is the encoder's skeleton with the load-bearing parts blanked. Each blank is a small
expression; the spec's description names every piece.

```python
def write_varint(n):
    out = b""
    while True:
        part = n & ____        # keep only the low 7 bits
        n = n >> ____          # drop the bits just taken
        if n != 0:
            out += bytes([part | ____])   # flag: more bytes follow
        else:
            out += bytes([part])
            return out
```

The reader is the same logic mirrored: take a byte, keep its low 7 bits, shift them into
place, and stop when the flag bit is clear.

</details>

### The full ping, against your own server

Assemble the handshake and the status request per the spec, send them, read the reply,
and parse it.

Done when: your script prints your own server's status — the motd you wrote, the version,
the player count — parsed from JSON with the `json` module, formatted so a person can
read it. Two working practices, stated plainly because they are the difference between
debugging and despair:

- Before sending, print your assembled packets with `.hex()` and check them against the
  spec's field tables by eye, field by field.
- The reply's JSON string announces its own length. `recv` gives you what has arrived,
  not what was promised — loop until you hold every promised byte, then parse.

If the server answers with silence, that is the silence-is-data lesson pointing at you:
some byte of yours broke the agreement, and the server owes you nothing. Hex out, spec
open, field by field.

### Across the internet

Point the same script at a big public server. Pick any famous one — the large public
servers publish their addresses on their own websites (the default port is 25565 when

Done when: the same JSON shape arrives from a machine you've never seen, run by
strangers, with — depending on the server — thousands of players online right now,

For the record: this request is exactly what the multiplayer screen sends to every server

## Break it on purpose

Four experiments — two on the files, two on the wire. Cause each one, read what happens,
and undo what needs undoing.

**Read a file while its owner is writing it.** This is the experiment behind the copies
rule. On your expendable server: start it, then run a small Python loop that loads the
*live* `world/level.dat` every couple of seconds and prints the time field — while
someone (you, in-game) lets time pass. Watch what the printed values do. Two different
kinds of wrong are possible: values that lag behind reality, and — if your timing lands
mid-write — an outright parse error on a half-written file. Run it for a while and record
what you actually observe; either outcome proves the point. The server keeps the real
world in memory and writes to disk only periodically, so the file on disk is always
somewhere between stale and momentarily torn. That, in one experiment, is why the first
half happened on a copy. Nothing to undo — reading never writes; stop the loop.

**Feed bytes to the wrong layer.** First do by hand what the NBT library has been doing
for you: use Python's `gzip` module (`gzip.open(path, 'rb')`) to decompress `level.dat`
yourself, and print the first few bytes of what comes out — no longer `1f 8b`; you're
looking at the NBT layer's own opening bytes now. Then break it both directions: hand the
still-compressed raw file to the part of your code expecting decompressed NBT, and hand
the decompressed bytes to `gzip.open`. Read both errors completely, out loud, as always.
Notice what binary tools complain in: text tools gave you line numbers; binary tools give
you byte offsets, unexpected values, and magic numbers that didn't match. Same
error-reading skill you've been building since the first refused startup — different
units.

**Lie about the protocol version.** In the handshake, claim something absurd — a protocol
version no client has ever had. Send the status request as usual. Does the reply still
come? You watched the server refuse mismatched *joins* instantly in
[Choosing a version](../choosing-a-version/guided.md) — if status behaves differently,
articulate why it would have to. (Consider what the status reply is *for*, and who has to
be able to ask for it.) Put the real version back after.

**Wrong next state.** Send 2 instead of 1 as the handshake's next-state field, then send
your status request exactly as before. Read what comes back — an error, a disconnect
message, nothing? Whatever it is, here's what's happening: 2 means "I'm here to log in,"
so the server is now interpreting your status-request bytes *as if they were login
packets*. Same bytes, different meaning, because the conversation is in a different
state. Protocols aren't just formats — they're agreements about where you are in a
conversation. Put the 1 back.

## What just happened

Hold the two halves of this session side by side, because they are the same picture. The
file: gzip compression, wrapping NBT structure, wrapping meaning — a field called
`SpawnX` and Minecraft's contract with itself about what it means. The wire: varint
encoding, inside packet framing, inside JSON meaning. Encoding, framing, meaning — a file
at rest and a conversation in motion, and both came apart into the same three layers,
each documented somewhere, each with a tool. You did it twice in one sitting. Once is a
trick; twice is a pattern: expect every format and every protocol you ever meet to
decompose this way, because they all do. Gibberish just means you haven't identified the
layers yet.

Everything above the socket was always just bytes in agreed shapes. RCON — bytes in an
agreed shape, with a password field. Mineflayer — a very large pile of code implementing
thousands of pages of agreed shapes, so that you could write `bot.chat()` instead of
this. The web — bytes in an agreed shape called HTTP. A library is someone who read the
spec so you don't have to, and you have now been that someone once. Every library you use
from here on looks different: not magic, just somebody's hours.

The details you fought with all exist for reasons you've now touched. Varints, because
small numbers are overwhelmingly common and spending four bytes on the number 1 wastes
three. Length prefixes, because a byte pipe has no boundaries — `recv` taught you that —
so every message must carry its own edges. And the handshake's hostname field: notice
that the name you typed travels to the server in plaintext, readable by whatever machine
answers. That is precisely how one machine at one shared address can host or front many
servers at once — it reads the hostname out of each arriving handshake and routes the
connection to the world that name means. If you have ever used a hosting service or relay
where many servers share one address and wondered how it knew which world was yours: it
read the answer out of these exact bytes.

About trees: NBT is compounds holding tags holding lists — nested, exactly like JSON's
objects holding keys holding arrays. Same shape, two encodings: JSON spends its bytes on
human-readable text, NBT spends them on compact binary. You have now read the same data
shape in both, and that shape — the tree — is most of what there is to structured data
anywhere.

And the map is worth pausing on, because it's a shape of payoff you'll want again: data
became a picture. Bytes nobody could read became an image anybody can. A script that
turns raw data into something a non-programmer immediately understands is a complete,
repeatable move — and you now own it end to end, from `1f 8b` to PNG.

## Go further

- **The block census.** The terrain itself lives in `world/region/*.mca` — "Anvil" region
  files, a genuinely deeper format with offset tables and per-chunk compression inside.
  Libraries for it exist on PyPI (search "anvil"); run the same evaluation you ran for
  the NBT library, and try the big one: count every block type in the entire world. How
  many diamonds exist, total?
- **The accidental time series.** Your dated backups each contain a `playerdata/` folder
  — positions at different moments in history. Realize what your backup archive has
  quietly become: a record of movement over time. Plot every backup's positions on one
  image, oldest to newest. What does weeks of wandering look like?
- The status JSON often includes a `favicon` field: the little server icon, travelling as
  text. It's a PNG encoded in base64 — bytes disguised as text so they can ride inside
  JSON. Python's `base64` module will give you the bytes back (there's a prefix to strip
  first — look at the field's value and you'll see it). Turn a famous server's icon into
  an actual `.png` file on your disk.
- Implement the first step of *joining*: next-state 2, then the login-start packet as the
  spec describes it, and read what the server sends back — the opening move of encryption
  negotiation. Then stop there. That wall is real cryptography, and it's worth seeing
  exactly where it stands with your own eyes.
- **The wealth map — and whether you should.** From region data, a map of where the
  diamonds are is technically reachable — including diamonds inside chests. Whose chests,
  though? Reading another player's chest contents from the files is something they
  couldn't do to you in-game. Is it fair play? There's no settled answer. Deciding what
  data you *should* read, separately from what you *can* read, is a real question that
  working with data never stops asking — and you've just reached the point where it
  applies to you.
- Genuinely open: your script can ping any Minecraft server on earth — but how would you
  *discover* servers you don't already know about? There's no index. People have scanned
  the entire internet's address space for port 25565 — whole projects have done it and
  published the results, and server owners have strong feelings about being found that
  way. Asking a published address for status is the intended use; knocking on every door
  on earth is something else. Where's the line, and who gets to draw it? There is no
  settled answer.
