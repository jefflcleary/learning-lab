# Reading the world itself

<!-- Generated from core.md. Substantive fixes belong in core.md; regenerate rather than fork. -->

## What this is

The server's logs were its diary — an account of what happened, written for humans.
The world folder is something different. It isn't an account of the world; it *is*
the world. Every block placed, every player's position, the time of day, the seed the
terrain grew from — all of it is sitting in files inside `world/`, and files can be
read by programs you write.

There's a catch, and this session meets it head-on: these files are not text. Open
one in an editor and you get gibberish, because the bytes don't encode characters —
they encode structure directly. That makes this the session where you learn to read
your first **binary format**, and it ends with something better than printed text: a
map. Every player's position in the world, plotted as labeled dots on an image you
can post where the people on it will see it.

## New tools

**NBT — Named Binary Tag** — is Minecraft's own file format for structured data.
It's a tree: named, typed entries nested inside each other, the same shape as the
JSON you've read before — but encoded as compact bytes instead of readable text.
`level.dat` (the world's global state) and every file in `playerdata/` are NBT.

**gzip** is a general-purpose compression format — same family as the `.zip` files
you've met. Minecraft compresses its NBT files with gzip, so there are two layers
between you and the data: gzip on the outside, NBT inside. You brushed against gzip
once before without naming it — the older log files in `logs/` end in `.gz` — and
today it gets handled properly. Python includes a `gzip` module in its standard
library, nothing to install.

A useful fact about compressed files: every gzip file begins with the same two bytes,
`1f 8b` (written in hexadecimal). Bytes like these are called a **magic number** — a
signature at the start of a file that announces its format, which is how tools know
what a file is without trusting its name.

**The `file` command** ships with macOS. Run `file somefile` in the terminal and it
reports what the file actually is, by reading its signature bytes.

**An NBT library from PyPI.** The leading candidate is called **nbtlib** — but
libraries change hands and go quiet, so part of this session is checking its current
state yourself before installing, exactly the way you evaluated a library in
[Choosing a version](../choosing-a-version/guided.md): README, issue tracker, recent releases.
The installing itself is the pip routine you already know.

**matplotlib** is the standard Python plotting library — it turns lists of numbers
into charts and images. Installed with pip like anything else. You'll use a tiny
corner of it: putting dots on axes and saving the result as a PNG. Its own
documentation covers the rest, and you'll be pointed there.

One rule frames everything below: **all of this happens on a copy of the world,
taken with the server stopped.** Reading can't damage files — but you'll prove to
yourself before the end of this session why reading live files can't be trusted
either.

## The work

### Take a safe copy

Stop your server. Make a working folder and copy the world into it:

```
mkdir -p ~/projects/world-lab
cp -r ~/projects/mc-server/world ~/projects/world-lab/world
```

(Adjust paths if your server lives elsewhere. Copying out of one of your dated
backups works just as well — a backup is a copy that already exists.)

You can start your server back up now if others want to play; everything below reads
the copy.

### Meet a binary file

Open `~/projects/world-lab/world/level.dat` in VS Code and read what VS Code tells
you about it.

Then look at the raw bytes yourself. In Python (a one-liner in the interactive
prompt is fine):

```python
print(open('/Users/YOURNAME/projects/world-lab/world/level.dat', 'rb').read(4))
```

The `'rb'` means "read bytes" — you're asking for the bytes as they are, not as
text. Look at the first two. Then ask the terminal's opinion:

```
file ~/projects/world-lab/world/level.dat
```

Three observations: what VS Code said, what the first bytes are, what `file`
reported. Search the web for "gzip magic number" and put the three together into one
sentence about what this file is. That sentence — *this is a gzip-compressed file
containing NBT data* — is the whole key to the session. Not all files are text; this
one is layers, and each layer is documented and openable.

### Choose and install the NBT library

Your goal: an NBT library installed in a fresh venv in `~/projects/world-lab` —
chosen after you've checked its current state, not on this page's say-so.

The candidate to start with is **nbtlib**. Before installing, evaluate it the way
you evaluated a library once before: find it on PyPI and GitHub, and answer — what
does the README claim? When was the last release? Is the issue tracker alive —
questions getting answers, bugs getting fixed? If nbtlib turns out healthy, install
it. If it turns out abandoned, find what the community moved to — searching PyPI for
"nbt" gives you the field of candidates, and the same three checks sort them.

### Print the whole tree, then scroll it

Load the copy's `level.dat` with the library and print the entire structure. Then

You're seeing how much state a world carries, which is the fastest way to know what

Check your five-item prediction against what's actually there.

### Excavate three facts and verify them in-game

From the tree, extract three things:

1. **The world spawn point** — three coordinates.
2. **The time** — and note there's more than one time-like field in there.
3. **The seed** — you met it as a settings key in
   [The server is yours to change](../server-settings/guided.md); now dig the actual number
   out of the bytes.

Then verify each one against reality. Start your server, join, and check: a vanilla
compass points to the world spawn — follow it and compare coordinates with the F3
debug screen. In the server console, `time query daytime` tells you the time of day,
and `seed` tells you the seed. Every number your script printed should be
confirmable by the running game.

<details>
<summary>Can't find them in the tree</summary>

You already scrolled past all three. Scroll again with three words in your head:
spawn, time, seed. Two of them have names close enough to English to jump out.

</details>

<details>
<summary>Closer pointers</summary>

The spawn is three values sharing an obvious prefix. Time appears under two
different names — one counts the world's total age, one counts the time of day;
compare both numbers against `time query daytime` and work out which is which. The
seed may sit a level or two deeper in the tree than the other two.

</details>

<details>
<summary>The reference</summary>

The minecraft.wiki page on `level.dat` documents every field in this file — the
same move as the `server.properties` page, for a different file. Search the wiki
for `level.dat`.

</details>

### Whose file is whose

Now `playerdata/`. One file per player who has ever joined — but the filenames are
UUIDs. A **UUID** (universally unique identifier) is a huge random number written as
hex with dashes. The files are keyed by UUID instead of player name for a simple
reason: names can change — Mojang lets players rename — and the UUID never does. If
the files were named by player name, a rename would orphan someone's entire
inventory.

Your goal: for each file in your copy's `playerdata/`, determine which player it
belongs to — by matching facts inside the file against facts you can check in-game,
not by asking the internet.

<details>
<summary>What kind of fact could match?</summary>

Each file records things a player could check about themselves while standing in
the world. Open the F3 debug screen in-game and look at what it shows you. Which of
those things must the file also contain?

</details>

<details>
<summary>The matching fact</summary>

`Pos` holds three numbers — x, y, z, exactly what F3 displays. One thing to keep
straight: your copy is a snapshot. The positions in it are where players were when
you made the copy, not where they are right now. Experience level and what someone
was carrying make good cross-checks.

</details>

<details>
<summary>A cross-check the server keeps for you</summary>

The server itself needs to map names to UUIDs, and it keeps its notes in a JSON
file in the server folder — and you can read JSON. Look through the server folder's
top level for a likely filename, open it, and use it to check the matching you
already did by hand.

</details>

### The map

The centerpiece. Every player's position, as one image: a labeled dot per player,
the world spawn marked, saved as a PNG.

Install matplotlib into the venv (the pip routine — nothing new). Then write the
script: collect each player's position and name, plot, label, save.

Done when: an image file exists that opens in Preview, shows a dot for every player
with their name next to it and the spawn marked, and would mean something to the
people whose dots are on it. That last part is the real test — post it where they'll
see it.

<details>
<summary>Three coordinates, flat map</summary>

A map is a top-down view, so it uses two of the three coordinates. In Minecraft,
which of x, y, z is height?

</details>

<details>
<summary>The plotting calls</summary>

Plot x against z. The three matplotlib pieces you need: `scatter` puts dots at
coordinate pairs, `annotate` (or `text`) puts a label next to a point, and
`savefig` writes the image to a file. matplotlib's own documentation shows each
one's arguments — that lookup is yours to do, and it's a small one.

</details>

<details>
<summary>The shape of the script</summary>

Loop over the files in `playerdata/`, load each, collect x, z, and the player's
name into lists. One `scatter` call with the collected coordinates (or one per
player), then the labels, then `savefig('map.png')`. When it's done, hold it next
to an in-game map — if north and south look mirrored, you've noticed something
real; Go further picks that thread up.

</details>

## Break it on purpose

Cause each one, read what happens, and note there's nothing to undo — reading never
writes.

**Read a file while its owner is writing it.** This is the experiment behind the
copies rule. On your expendable server: start it, then run a small Python loop that
loads the *live* `world/level.dat` every couple of seconds and prints the time field
— while someone (you, in-game) lets time pass. Watch what the printed values do.
Two different kinds of wrong are possible: values that lag behind reality, and — if
your timing lands mid-write — an outright parse error on a half-written file. Run it
for a while and record what you actually observe; either outcome proves the point.
The server keeps the real world in memory and writes to disk only periodically, so
the file on disk is always somewhere between stale and momentarily torn. That, in
one experiment, is why this whole session happened on a copy.

**Feed bytes to the wrong layer.** First do by hand what the NBT library has been
doing for you: use Python's `gzip` module (`gzip.open(path, 'rb')`) to decompress
`level.dat` yourself, and print the first few bytes of what comes out — no longer
`1f 8b`; you're looking at the NBT layer's own opening bytes now. Then break it both
directions: hand the still-compressed raw file to the part of your code expecting
decompressed NBT, and hand the decompressed bytes to `gzip.open`. Read both errors
completely, out loud, as always. Notice what binary tools complain in: text tools
gave you line numbers; binary tools give you byte offsets, unexpected values, and
magic numbers that didn't match. Same error-reading skill you've been building since
the first refused startup — different units.

## What just happened

File formats are contracts. gzip is a contract about how bytes get compressed; NBT
is a contract about how a tree of named values becomes bytes; the meaning of a field
called `SpawnX` is Minecraft's contract with itself. The "unreadable" file you
started with was three contracts stacked — gzip wrapping NBT wrapping meaning — and
you read it with one tool per layer: the gzip module for the outside, the NBT
library for the middle, and your own knowledge of the game for the top. Every opaque
file on every computer is this same picture: layers, each documented somewhere, each
with a tool. Gibberish just means you haven't identified the layers yet.

About trees: NBT is compounds holding tags holding lists — nested, exactly like
JSON's objects holding keys holding arrays. Same shape, two encodings: JSON spends
its bytes on human-readable text, NBT spends them on compact binary. You have now
read the same data shape in both, and that shape — the tree — is most of what there
is to structured data anywhere.

And the map is worth pausing on, because it's a shape of payoff you'll want again:
data became a picture. Bytes nobody could read became an image anybody can. A
script that turns raw data into something a non-programmer immediately understands
is a complete, repeatable move — and you now own it end to end, from `1f 8b` to PNG.

## Go further

- **The block census.** The terrain itself lives in `world/region/*.mca` — "Anvil"
  region files, a genuinely deeper format with offset tables and per-chunk
  compression inside. Libraries for it exist on PyPI (search "anvil"); run the same
  evaluation you ran for the NBT library, and try the big one: count every block
  type in the entire world. How many diamonds exist, total?
- **The accidental time series.** Your dated backups each contain a `playerdata/`
  folder — positions at different moments in history. Realize what your backup
  archive has quietly become: a record of movement over time. Plot every backup's
  positions on one image, oldest to newest. What does weeks of wandering look like?
- **Map the Nether.** The other dimensions live in their own folders inside the
  world folder. Find them, and make the second map.
- **The wealth map — and whether you should.** From region data, a map of where the
  diamonds are is technically reachable — including diamonds inside chests. Whose
  chests, though? Reading another player's chest contents from the files is
  something they couldn't do to you in-game. Is it fair play? There's no settled
  answer. Deciding what data you *should* read, separately from what you *can*
  read, is a real question that working with data never stops asking — and you've
  just reached the point where it applies to you.
